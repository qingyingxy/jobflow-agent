# AI Campus JD 技能标注规范 v1

- 版本：`ai-campus-annotation-guide-v1`
- 生效日期：2026-09-02
- 适用范围：AI 校招 JD 的 `required_skills`、`required_skill_groups`、
  `preferred_skills` 与 `skill_mentions`
- 原则：只依据当前样本中的 JD 原文标注；公司、岗位名称或模型预测都不能补充原文
  没有表达的要求。

## 1. 标注单位

以一个具有共同强度和逻辑关系的原文条款为最小判断单位。先判断强度，再判断关系，
最后抽取原子技能：

```text
原文条款 -> required / preferred / mention -> all_of / any_of -> 原子技能
```

一个技能必须能由连续原文片段支持。职责、学历、专业、软技能和经历背景不能仅因与技术
相关就自动变成技能标签。

## 2. 强度规则

### 2.1 `required_skills`

标注候选人必须同时满足的直接技术要求。以下未被弱化或转折的表达通常属于必备：

- 必须、需、要求、掌握、熟练掌握、熟悉、精通、具备、能够；
- “理解 A”且没有“基本、一定、初步、简单”等弱化词；
- “有 A 经验”“具备 A 经验”等直接资格要求；
- 同一必备条款内由“和、及、以及、并”连接的独立技能。

例：`熟悉 Python 和 SQL` 标为两个 `required`、`all_of` 技能。

### 2.2 `preferred_skills`

只标注原文明示优先或加分的原子技术能力或技术项目经验，例如“优先、加分、最好、
有……者优先”。优先条件不是硬门槛。

- `了解 A，有 B 经验者优先`：A 为 `mention`，B 为 `preferred`。
- `了解 A 者优先`：整个条件受“优先”支配，A 为 `preferred`。
- 论文发表、竞赛获奖、兴趣倾向不计入 `preferred_skills`。

### 2.3 `skill_mentions`

标注原文出现但不构成独立硬门槛或加分条件的技术概念，主要包括：

- “了解、基本了解、一定理解、初步理解”等弱认知要求；
- 岗位职责中的技术方向、工作对象或待完成任务；
- “如、例如、包括但不限于”等引出的产品、框架或算法示例；
- `any_of` 组中的具体选项，用于保持词面追溯；
- 被上位要求覆盖、不能再独立计为硬门槛的子项。

`skill_mentions` 用于检出率和追溯评估，不表示候选人必须掌握该技能。

## 3. 关系规则

### 3.1 `all_of`

普通并列要求使用 `all_of`。没有明确选择语义时，不得根据常识将多个技能改成备选组。

- `熟悉 Python、SQL`：两项都必备；
- `具备训练和部署经验`：训练、部署都必备；
- “包括但不限于”只表示示例不封闭，本身不表示候选人任选其一。

### 3.2 `any_of`

仅当必备条款明确表示“满足至少一个”时建立 `required_skill_groups`，典型信号包括：

- 至少一种、任一种、任一项、任选其一；
- A 或 B、A/B 中的一种；
- 从若干项中选择、任一方向均可。

组格式为：

```json
{
  "name": "编程语言",
  "any_of": ["Python", "C++"],
  "allow_other": false
}
```

`allow_other=true` 仅用于原文包含“等、之一、包括但不限于”并明确允许未列出的同类选项。
否则为 `false`。显示名称和选项顺序不参与关系正确性判断。

优先或弱提及条款即使含有“或”，也不建立必备 `any_of` 组；其选项分别放入
`preferred_skills` 或 `skill_mentions`。

## 4. 粒度与歧义

- 上位类别和它的示例子项不能混在同一个 `any_of` 中。例如“熟悉深度学习框架，
  如 PyTorch/TensorFlow”标上位要求为 `required`，框架名为 `mention`，不能组成
  `[深度学习框架, PyTorch, TensorFlow]`。
- 近义词或上下位词之间出现“或”时，先按原文保留原子概念；只有确实表达候选人可满足
  其中任一项时才建组。若只是同一概念的改写，统一为一个规范标签，不建组。
- 复合能力只有在原文把它作为单一概念时保留，例如 `LLM Agent`。不能为了提高匹配率
  擅自拆成 `LLM` 与 `Agent`，也不能把普通并列随意合并。
- 学历、专业、论文、竞赛、兴趣，以及沟通、协作、学习能力等软技能不进入四个技能字段。

## 5. 规范化与别名

规范化只消除词面差异，不改变语义强度、关系或粒度。

- 安全别名：缩写、大小写、空格或明显同词变体，例如 `TS -> TypeScript`、
  `Golang -> Go`、`力控 -> 力控制`。
- 语义等价映射：必须有单独规则和人工证据，不能仅凭“意思接近”处理。例如
  `多端项目 -> 多端开发` 不是自动安全别名。
- 上位类别与具体框架不是别名，例如“深度学习框架”不自动等于 PyTorch。
- 新映射必须加入版本化词表和测试；不得只为某个评测样本增加隐式特例。

## 6. 标注流程

1. 保留完整 JD 原文和来源信息。
2. 独立标注岗位类型与地点，再按条款标注技能强度和关系。
3. 对每个技能保存原文依据；存在歧义时记录复核说明，不参考模型 prediction。
4. 第二人或第二轮复核 `any_of`、强度边界、复合词和别名。
5. 在生成 prediction 前冻结标签版本、样本 ID 与划分文件。
6. 冻结后不得静默编辑标签。争议修订必须创建新的标签版本并记录理由；历史冻结标签、
   prediction 和 report 保持不变。

## 7. 评测口径

- 技能检出：忽略强度，判断技术概念是否被识别。
- 技能强度：分别评估 `required`、`preferred`、`mention`；`any_of` 组选项不参与强度
  分类，避免将条件备选项误当作逐项硬门槛。
- `any_of` 关系：在存在标准组的样本上计算条件完全匹配率，并在无标准组样本上报告
  误建组率。
- 岗位类型、地点和旧字段 F1 继续保留；新拆分指标用于解释错误来源，不替换历史指标。

## 8. 版本管理

本文件是首个可执行口径。任何会改变标签含义或指标分母的规则调整，都必须升级版本并
记录迁移说明。只补充不改变语义的示例可做勘误，但仍需留下提交记录。
