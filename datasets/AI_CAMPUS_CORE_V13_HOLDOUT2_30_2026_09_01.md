## 主要误差

### 1. 基础字段已经稳定

`job_type` 和 `locations` 均为满分，30 条逐例完全匹配。当前不需要继续针对这
两个字段优化。

### 2. 必备技能仍受本体与粒度不一致影响

`required_skills` 有 52 个 FP 和 62 个 FN，30 条均未达到整条精确匹配。典型
差异包括：

- `017`：原文 `ReAct` 仍被模型输出为前端 `React`，同时将 CoT、
  Plan-and-Execute 和强化学习提升为硬门槛；
- `063`：`机理与数据融合建模`、`算法工程化` 与模型输出的更细粒度描述不能
  严格对齐；
- `071`：`深度学习框架` 被输出为 `主流AI框架`，`LLM API` 和数据预处理被
  支持校验删除；
- `110`：`Agent框架`、`低代码平台` 被合并为 `AI应用开发框架`；
- `161`：`深度学习框架` 被输出为 `深度学习`。

这说明下一轮必须先固定共享技能本体和上下位类别，而不是继续逐条追加 Prompt
示例。

### 3. `any_of` 仍有 8 条结构差异

主要失败样本为 `033`、`035`、`067`、`083`、`112`、`130`、`144`、`161`：

- `033` 正确识别语言组，但额外创建 Agent 框架组；
- `035` 改写组选项并错误设置 `allow_other=true`；
- `067` 和 `112` 漏掉明确备选组；
- `083` 把独立必备的 Python 合并进 C++/C# 组，并改写 AI 实践组选项；
- `130` 漏掉 C；
- `144` 存在 `TypeScript/TS` 别名、开放性和第二组选项改写问题；
- `161` 把 `图像生成` 扩写成 `图像生成项目经验`，导致整组严格失配。

### 4. 加分项以漏召回为主

`preferred_skills` 的 Precision 为 0.6696，Recall 仅 0.4601，共有 88 个 FN。
长加分段、技术项目经验和同一句中的多个原子能力经常只召回一部分。`071`、
`085`、`130`、`132`、`139` 等样本尤其明显。

### 5. 原文支持校验仍过于依赖连续字符串

24/30 条样本触发了 `unsupported_field_value`，共 65 次。部分删除是正确的，
例如删除语言类岗位中的非技术资格或模型扩写；但也误删了 `LLM API`、数据预处理、
工程能力、高性能系统、AI 工具使用等具有原文语义支持的归一化结果。

支持校验需要继续坚持“无证据即删除”，但应增加可审计的别名、共享后缀枚举和
上位类别证据映射，不能简单放宽为模糊匹配。

## 决策

当前不运行完整 154 条。本批已经足以证明 Parser v13 尚未达到既定门槛；继续
全量调用只会增加费用，不会改变是否通过的结论。

建议后续按以下顺序处理：

1. 修复 `ReAct -> React` 的大小写语义误判，并补回归测试。
2. 建立 gold 与 prediction 共用的受控技能本体，统一上位类别、别名和粒度。
3. 对上述 8 条 `any_of` 差异提炼通用结构规则，不写 case-id 特判。
4. 改善长加分段的原子技能召回，并保持必备优先于加分项。
5. 扩展可审计的原文支持映射，分别统计模型原始输出和校验后输出，确认校验器的
   正向收益与误删率。
6. 将本批转为诊断集。修复后从剩余 64 条真正未见样本中抽第三批 holdout；只有
   新 holdout 达到门槛后，才运行完整 154 条。

不能直接在本批预测结果上回改标签后把它继续作为最终 holdout，否则会破坏未见
评测的可信度。
