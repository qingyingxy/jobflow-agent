# 候选人事实保留与普通要求匹配

更新：2026-10-08。此文描述当前实现，不代表新增准确率评测结果。

普通能力模型匹配的历史开发对照见 [秋招模型匹配实验](CAMPUS_MATCHING_PILOT.md)。当前已增加可选的生产接入：本地生成句子编号、每岗一次批量判断、引用回填与校验、超时降级及缓存。默认仍为 `local`；`semantic` 需要明确启用，不会自动发送新增的经历匹配请求。历史实验输出和指标没有覆盖更新，也不能作为新提示词的准确率成绩。

## 默认不打断用户

- 简历抽取仍使用已有模型请求；默认本地匹配、身份合并、冲突识别不增加模型请求。选择语义匹配时仅普通能力判断增加批量模型请求。
- 有完整直接证据的条件自动通过；只有相关技能的条件显示“部分支持”；没有直接证据或无法可靠确定条件关系时显示“信息不足”。缺失证据不等同于不具备能力。
- 信息不足不会使本次分析失败，不要求用户逐条回复才能继续。资格和投递原有的约束仍适用。
- 导入新简历时保留用户修正，界面用可展开的差异列表展示新资料；普通保存不等于接受新值，也不等于确认冲突。
- 用户可以编辑当前值，或选择“保留当前值”；教育经历的选择随“保存简历资料”提交。相同差异不重复提醒。

## 普通要求：关键词只用于寻找证据

入口：`src/services/local_evidence_matcher.py`；规则：`ordinary_requirement_evaluator.py`。

以前一旦技能命中就跳过其他文字。现在以完整 `description` 为条件来源，避免简短 `items` 丢失限定。只执行可证明的有界文本关系：

- 技能别名归一化时保留经验、原理、能力、独立性等限定。
- 年数和月数按月份比较；中文数字、明确的熟练程度采用本地规则。年限只与同一证据句中的其余条件绑定，不跨经历累加，也不借用另一技能的年限。
- 只接受明确肯定的经历描述，技能标签和模型生成标题不能单独证明要求。否定、计划、招聘要求等不作为经历证明。
- 职责、项目类型、成果和剩余限定必须仍有文本证据。无法理解的改写保留为不确定，不靠技能重叠兜底通过。
- 能与原文连续选项列表对齐的 `any_of`/`all_of`，保留共同前缀、后缀；分支完整满足后才聚合。复杂、无法对齐的任选范围不执行为通过。

例如“熟练掌握 Python，并有三年线上系统开发经验”对“使用 Python 写过课程脚本”，返回 `partial`；对“熟练掌握 Python，有五年线上系统开发经验”，可自动返回 `supported`。

`RequirementMatch.item_checks` 保存原始 JD `source_text`、实际执行的 `condition_text`、证据 ID、简历原句、已发现的技能和尚无完整支持的限定。展开匹配结果可以看到依据。`validation_status=passed` 表示结构有效，不表示资格已经通过。

这不是通用语义推理器。复杂嵌套、跨句省略、多段重叠工龄、多数隐含能力及任意同义改写可能仍无法证明；不会为减少提示而猜测通过。已有教育类型化规则继续走独立链路。

## 可选的语义匹配与统一入口

搜索后的自动分析和按钮触发的手动分析共用 `analysis_runtime.create_analysis_service`。它们使用相同的解析模式、教育谓词、缓存和匹配配置；不再分别构建不同版本的解析器。

```dotenv
EVIDENCE_MATCHING_MODE=local
EVIDENCE_MATCHING_TIMEOUT_SECONDS=60
```

确认将已保存的经历原句、标题和技能标签交给所配置的模型服务后，可显式改为 `semantic` 并重启后端。模型沿用 `STRUCTURED_MODEL_PROVIDER`、`LLM_BASE_URL`、`LLM_MODEL`。2026-10-08 用户确认授权后，当前本地 `.env` 已启用 `semantic`，项目默认值和示例配置仍为 `local`。资格条件中的学历与专业继续由本地类型化规则处理，地点及岗位方向属于本次搜索条件。

`semantic_evidence_matcher.py` 为每条经历原句生成稳定编号。模型收到完整普通要求和当前用户的经历句子，一次返回全部要求的支持程度、解释、缺失项及句子编号。本地检查要求索引完整性、引用归属，回填对应的真实原句。不存在的引用只降级受影响的要求；索引缺失、重复或越界则降级整个批次。原文可追溯不等于推理一定正确。

无经历时直接返回信息不足，不发请求。单批上限为 80 条要求、60 条经历及 60,000 字符的完整请求；超过容量不会截断后给肯定结论。默认总超时为 60 秒（可配上限 120 秒），无 HTTP 自动重试和校验修复。超时或无效输出保留岗位、资格检查和有效匹配，受影响项显示信息不足；未完成的必须条件不会显示为完整推荐。

有效匹配存入现有 `AgentRun`，缓存绑定用户、岗位、要求全文、经历内容以及模型/provider/endpoint/提示词/schema/推理配置。相同完整输入复用分析；只改教育资料时可复用仍有效的能力匹配。失败不会永久缓存，再次分析只重试未成功的匹配，不重复已成功的 JD 解析。模型等待期间资料或岗位变化时拒绝发布旧结论（HTTP 409）。

搜索中的明确排除条件由 `search_constraints.py` 保留到所有补搜查询，并由本地筛选分别处理城市、招聘类型和岗位方向。例如“只考虑上海，不考虑北京”不会被展开成北京的正向查询。多工作地点包含上海的岗位仍保留上海选项；明确排除项归入前端默认折叠的“明显不符”组。规则仅覆盖已有词表和明确否定句式，不能完整解释“除非、最好、如果”等任意条件偏好。网页中明确标注的招聘类型可覆盖表示工作时间的 `FULL_TIME`，但普通经历要求里出现“实习”不会据此覆盖招聘类型。

## 事实合并：自动值与人改值分开保存

`FactProvenance` 包含最近的 `extracted` 基线、用户修改的 `overrides` 字段、未处理的 `conflicts` 和已处理差异的摘要 `acknowledged`。这些数据由服务端维护，普通前端保存不能覆盖它们。

教育经历编辑按 ID 与已保存值比较。只修改过的字段覆盖下一次自动抽取；未修改的字段可以自动更新。旧记录仅有整段 `reviewed` 而没有字段历史时，保守保留整段事实；毕业年份的显式确认同样保留。

合并教育经历优先使用原文一致，其次要求明确的学校、入学年份和学历共同对应，而且新旧双方必须唯一。只有学历相同不合并。无法区分是否重复的记录保留为差异，不新增另一条可用于通过资格的学历。明确不同学校的新经历可以新增。

项目等一般经历用抽取原句唯一对应，保留 ID 及用户修改字段；原句变化但名称和类型与受保护经历一致时，保留旧值并记录待处理差异，不直接覆盖。没有可靠关联的新记录不会被强行合并。

已修改但在新简历中省略的经历仍保留。明确移除的教育原文/身份、项目原句记录在导入状态中，同一记录再次出现不会自动复活。全新的措辞且缺少身份锚点时，仍可能无法识别为同一被删除记录。

`education_history_complete` 仅在历史记录集合仍可确认未变化时保留；新增、替换或无法唯一对应时回到不完整。`resume_import_state.source` 单独记录当前抽取资产，因此保留旧来源的修正记录不会导致重复调用模型。

旧一般经历没有编辑历史时，仅能依据其既有更新时间保守识别编辑；无法恢复过去已被覆盖的修正。元数据是当前基线与差异记录，不是完整事件审计日志。
