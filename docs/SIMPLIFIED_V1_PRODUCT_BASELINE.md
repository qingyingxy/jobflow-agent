## 2. 为什么改造

当前主流程大致为：

```text
多公司 Adapter 搜索
-> 自动选择 Top 5
-> Core / Detail / Staged / Full 等多阶段 JD 解析
-> 每条 requirement 分别调用模型匹配简历证据
-> 计算 0～100 总分
-> 材料、投递包、ATS、回执和跟进
```

当前实现的问题：

- [x] 产品主线和 `v1～v39` Parser 实验混在一起，理解和维护成本高。
- [x] `JDAnalysisService` 在解析 JD 后，还会为每条 requirement 单独调用一次模型；一个包含 8 条要求的岗位可能产生约 9 次模型调用。
- [x] “全局 Top 5”会让用户误以为系统已经完成可信的跨公司排序，实际还可能需要再次读取和解析岗位。
- [x] `0～100` 总分掩盖了硬性资格、必须条件、优先条件和信息缺失之间的差异。
- [x] ATS、材料生成、投递包、回执和自动跟进超出了当前最需要验证的产品闭环。

## 3. 第一版目标与边界

第一版只验证以下闭环：

```text
可信岗位发现
-> 每份 JD 先提取事实与条件，再集中判断条件关系
-> 真实经历匹配
-> 用户选择并记录
-> 用户在官网手动投递
```

- [x] 用户负责选择岗位和执行最终投递。
- [x] Agent 不自动提交申请、不自动修改简历，也不虚构经历。
- [x] 系统分析“这个岗位应该突出什么以及为什么”，不直接要求用户突出固定的 2～4 段经历。
- [x] 一次只处理一家公司，不扫描 40 家公司后做全局 Top 5。
- [x] 每家公司最多处理 3～5 个已验证的具体岗位；不足时展示实际数量，不用无效岗位凑数。
- [x] 用户可以同时选择多个岗位准备申请。

## 4. 目标用户流程

```text
首次设置目标和简历
-> 输入或选择一家公司
-> Agent 搜索该公司的官方具体岗位
-> 验证官方来源、开放状态和正文完整性
-> 保存完整 JD 快照
-> 每份 JD 调用提取 API 一次，再调用关系判断 API 一次
-> 本地编译技能字段并匹配简历证据
-> 展示 3～5 个岗位的可解释对比
-> 用户选择一个或多个岗位
-> 用户在官网手动投递
-> 在本地看板记录后续状态
```

## 6. UnifiedJDParser 契约

### 6.1 模型输出

- [x] 产品运行时只使用一个 `ProductJDParser` 对外编排两个固定阶段。
- [x] 每份含条件的 JD 正常进行两次模型调用：一次提取，一次集中判断全部条件关系。
- [x] 第一阶段只输出 facts、条件原文与强度、职责；第二阶段只输出关系、items 和理由。
- [x] 公司、岗位名称和申请 URL 使用已经验证的网页数据，不让 Parser 猜测。

`facts` 固定为 9 项：

1. `job_type`
2. `locations`
3. `graduation_years`
4. `education_requirements`
5. `major_requirements`
6. `internship_duration_months`
7. `weekly_days`
8. `earliest_start_date`
9. `deadline`

其中 `internship_duration_months`、`weekly_days` 和 `earliest_start_date` 仍由首次提取阶段保留原文证据，但只用于岗位信息展示，不参与简历自动匹配、建议档位或淘汰。是否远程、是否可转正等未单列字段的信息直接从已保存的 JD 原文展示，不新增 Parser 字段，也不再次调用 API。

关系判断阶段表达：

- [x] `required`：明确必须满足。
- [x] `preferred`：出现“优先、加分、具备更佳”等表达。
- [x] `mention`：职责或上下文提及，但不是明确资格条件。
- [x] `all_of / any_of` 等逻辑关系。
- [x] `uncertain`：API 无法可靠确定关系时保留待确认，不由本地规则猜测。
- [x] “至少掌握一种”“包括但不限于”等开放组。
- [x] 年限、项目、行业或使用经验等限定条件。
- [x] 每条 clause 必须引用连续的 JD 原文证据。

### 6.2 本地编译

- [x] 本地代码从 clauses 编译 `required_skills`、`required_skill_groups`、`preferred_skills` 等兼容字段。
- [x] `required_skill_groups` 表达必须条件中的逻辑组，例如“Python、Java、Go 至少一种”，不能错误展开成三个都必须。
- [x] “XX 优先”进入 preferred 语义，不进入 required 字段。
- [x] 本地编译结果可以重建，不作为第二份人工维护的事实源。
- [x] 定义并冻结 Unified Parser 的 Pydantic Schema。
- [x] 实现 clauses 到兼容字段的确定性编译器。
- [x] 为 required、preferred、mention、any_of 和开放组补齐单元测试。

### 6.3 失败处理

- [x] 每个阶段返回后使用本地代码做 JSON、Schema、格式和证据校验。
- [x] 原文未提供某个字段时允许为空，并标记信息不足，不因缺失自动重试。
- [x] 只有当前阶段输出无法解析、违反 Schema 或引用不存在的原文时，才允许该阶段
  自动重试一次。
- [x] 重试请求必须携带具体校验错误。
- [x] 任一阶段修复后仍失败时停止并交给用户处理，不切换到旧 Parser。
- [x] 实现本地校验、有限重试和稳定错误码。

### 6.4 旧 Parser

- [x] Unified 未通过新盲测前，不提前替换当前稳定线上路径。
- [x] Unified 通过门槛后，线上只走 Unified。
- [x] Core、Detail、Staged、Full 和 `v1～v39` 仅保留离线复现所需代码、数据和结果。
- [x] 旧 Parser 不再获得新产品功能，也不作为线上失败回退。
- [ ] 完成旧 Parser 归档边界和运行入口清理。

## 8. 岗位分析与排序

分析页固定为三部分：

- [x] 这个岗位应该突出什么，以及对应的 JD 原文原因。
- [x] 用户简历中有哪些可以支撑的真实证据。
- [x] 缺口、风险和待确认信息。

不展示 `0～100` 总分，只展示四种建议：

- [x] `推荐申请`：没有硬性资格冲突，主要必须条件有真实经历支持，风险较少。
- [x] `可以考虑`：没有明确硬性冲突，但存在必须技能证据不足、方向偏差或竞争风险。
- [x] `不建议申请`：毕业年份、学历、地点或招聘类型等硬性条件明确冲突；不能仅因缺少一项技能而判定。
- [x] `信息不足`：JD 或用户资料缺少决定性信息。

排序规则：

- [x] 先判断毕业年份、学历、地点和招聘类型等硬性条件。
- [x] 再比较必须条件的真实证据覆盖情况。
- [x] 然后参考优先条件以及岗位方向与用户目标的一致性。
- [x] 最后参考截止时间和岗位信息完整度。
- [x] 同档位内优先展示硬性风险更少的岗位。
- [x] 每个结论必须展示触发它的 JD 原文和用户证据。
- [ ] 实现四档建议、排序规则和解释输出。
- [ ] 移除用户界面的总分展示。
