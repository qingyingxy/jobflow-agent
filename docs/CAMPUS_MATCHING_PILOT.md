# 秋招普通能力：规则与模型匹配对照

本轮只回答“已有 JD 要求和候选人事实固定时，模型是否比当前本地规则更适合判断普通能力”。主流程仍使用原有策略；新批量匹配器是实验组件。

## 预先固定的设计

- 来源：已开放的 Product JD development70 历史快照；不使用封存测试集。按固定 SHA-256 排序取八家不同公司的岗位，包含六个校招岗位和两个实习岗位。历史快照不代表岗位当前仍开放。
- 样本：八份 JD 的全部普通能力要求，共 61 条；五条专业条件明确排除。已有解析结果对两种策略相同，本轮不评估解析质量或完整资格判断。
- 候选人：`datasets/campus_match_candidate_v1.json`，一份明确标为虚构的固定资料。包含开发、模型训练、论文复现、组内协作，也明确说明没有实习、论文发表、高并发系统和真机操作等经历。不是用户简历。
- 参考：`datasets/campus_matching_pilot_v1.json`，运行前由编码代理拟定，未经过独立人工裁定。52 条为单一参考判断（31 支持、11 部分支持、6 明确不满足、4 信息不足）；9 条允许多个合理结果，单独统计，不计入严格参考指标。
- 输入公平：两边看到同样完整的当前用户经历，不使用不同检索器或不同 top-k；模型看不到参考标签、标注理由和规则输出。
- 模型：配置的 `gpt-5.6-terra`，medium、temperature=0、json_object。每个岗位一次批量请求，共最多八次；每次 60 秒，总预算 600 秒，不重试、不使用结果缓存。两种策略交替执行顺序。
- 运行前冻结样本、标签、模型参数、提示词及实现文件哈希。原始输出、失败、用量和耗时按岗位即时落盘，不覆盖已产生的报告。

## 模型与代码的责任

`src/services/batch_evidence_matcher.py` 让模型根据具体工作推断普通能力，不要求原文照抄“熟悉”等词。每条判断返回状态、解释、经历 ID、该经历内的原句引用及缺失条件。

本地代码检查输出覆盖、索引唯一性、引用归属和引用是否出现在指定 claim 中。错误引用降级为信息不足；超时也不判候选人不合格。标题和技能标签不构成事实引用。学历、专业的类型化条件仍交给本地资格检查。

引用通过校验，只说明原句存在，不能证明模型的能力推断、解释或正反方向一定正确。因此实验分别记录引用有效性与参考判断差异。

## 判据及边界

预先约定的积极信号：对单一非支持参考没有完全通过的判断；比规则多识别至少五条单一支持参考；原始引用及输出覆盖全部有效；每岗位 P95 耗时不超过 60 秒。所有条件满足也只是开发信号，不能据此宣称线上准确率，或自动切换生产默认策略。

统计严格参考的一致数、完整支持召回、把非支持参考判为完全支持的数量、歧义项、原始引用、失败及延迟。一次跑八个岗位的 P95 实际接近最大值，不代表稳定的生产分位数。

Token 只作为资源消耗记录。没有核实当前服务商的计费单价，因此不推算金额；失败请求可能没有返回用量。信息不足的数量也不是实际用户被打断次数。

## 复现

先运行离线单元测试，再冻结清单，然后运行真实请求。每次必须使用新的输出路径：

```powershell
.venv\Scripts\python.exe -m pytest tests/test_batch_evidence_matcher.py tests/test_campus_matching_comparison.py -q
.venv\Scripts\python.exe -m scripts.compare_campus_matching --output artifacts/evaluation/my-campus-freeze.json
.venv\Scripts\python.exe -m scripts.compare_campus_matching --live --manifest artifacts/evaluation/my-campus-freeze.json --output artifacts/evaluation/my-campus-results.json
```

冻结之后更改样本、标签、模型参数、提示词或实现文件，真实运行会拒绝继续，需要重新审查并生成清单。完整来源片段和模型输出保存在 Git 忽略的 `artifacts/evaluation/` 下，遵循原数据集的正文保存约定。

## 2026-10-08 实际结果

| 观察项 | 当前本地规则 | 模型批量匹配（经校验） |
|---|---:|---:|
| 覆盖 JD / 条件 | 8 / 61 | 8 / 61 |
| 31 条单一“支持”参考中判为支持 | 0 | 19 |
| 与 52 条单一参考完全一致 | 6 | 35 |
| 将单一非支持参考判为完全支持 | 0 | 1 |
| 模型请求 | 0 | 8 |
| 请求超时 | — | 1 |
| 每岗位中位耗时 | 0.37 秒 | 48.27 秒 |
| 本轮 P95（八份样本中等于最大值） | 0.71 秒 | 60.59 秒 |

模型原始判断识别出 20 条单一支持参考；其中 1 条因引用格式被降级，最终 19 条。原始引用 93 个，严格逐字检查通过 92 个。7 次成功返回的请求报告了 23,582 输入 token 和 10,652 输出 token，另 1 次超时未报告用量，不能把该总数当成全部计费量。没有金额估算。

一份包含 13 条要求的 JD 超时，导致 13 条都返回信息不足；它是一次请求失败，不是 13 次独立的语义判断错误。其余七份结果均有完整索引覆盖。预先约定的四项条件中，只有“多识别至少五条支持参考”满足，整体未通过。

零调用复核保留原标签、原输出，发现：

- 对语言任选要求，模型判断 Python 实践足够，本来符合参考。一个引用把原文分号改成句号，严格校验因此拒绝整条判断；引用没有增加新事实。这说明当前让模型重复抄写引用的方式会造成不必要降级。
- 一条“深入理解 AI 产品”的要求，模型认为研发、微调及产品思考足以支持，参考认为只能部分支持。缺少独立裁定，不能将此报告为确定的真实误判。
- 对“独立分析”“从需求定义产品”“优秀英文阅读”“代码规范”等条件，模型多次比参考保守。复核发现参考理由对“独立”的陈述也比候选人原文更强，后续需要同时审查参考与模型，不能只改提示词去迎合标签。
- 实际工程、论文复现和团队协作可支持能力推断；当前规则几乎只接受明确程度词或原文模板，所以在这批校招条件中过于保守。

工程结论：普通能力匹配值得以模型作为后续主路径候选，明确硬资格继续本地判断。本轮仅交付实验组件，没有接入默认分析。下一轮优先做简短判断与本地证据编号回填，减少模型重复输出引用；明确秋招程度词的证据标准；再用新增候选人及独立标注样本验证。不能只扩充同一候选人上的关键词规则，也不能将本轮 19/31 或 35/52 宣称为产品准确率。
