# 北京上海 Agent 与 RAG 校招真实试用

2026 年 10 月 16 日，按“2027 届，北京或上海，AI Agent / RAG 校招，排除实习和社招”完成两轮真实岗位搜索，以及收藏、岗位原文、个人匹配、申请记录和材料草稿流程。结论：已能帮助找岗位和整理申请，但筛选仍存在漏收和误收，不能把“符合已知条件”直接理解为“适合本人投递”。当前优先改进判断质量和故障恢复，无需继续堆功能。

## 试用范围和结果

使用原数据库与私密文件的本地副本，原业务代码未修改。岗位搜索使用现有真实官网来源与配置的模型服务，保持 300 秒、6 轮、目标 15 个岗位的预算；未使用固定招聘站点响应。个人经历匹配单独切换为本地模式，公开 JD 仍由真实模型解析。因此，下述个人匹配问题适用于本地模式，不代表默认语义匹配的实测质量。

正式校招试用前曾进行北京实习预试用；它不计入以下两轮结果，但留下的已保存岗位会被目标岗位库重新筛选。首轮不是空库测试。

首轮服务端在约 10.89 秒记录第一个有效岗位；这是后端追踪时间，不是浏览器首屏计时。重复更新前读取已有目标结果耗时 1.70 秒。第二轮 63 条线索与 62 个筛选岗位是不同统计口径，未将它们当成相同数量。

首轮核验来源包括字节、小米、蔚来、MiniMax、京东、百度；27 个符合结果全部来自字节 13 个、蔚来 8 个、小米 6 个。找到了有用岗位，但这两轮不足以证明已覆盖北京、上海市场，也不能据此计算全网召回率。

已验证的行为：

- 输入正确保留北京与上海两个可选城市、2027 届和校招，旧北京实习偏好没有覆盖新条件。
- 可以浏览逐条筛选依据和完整原文，打开官网核对。明确的实习岗位被排除，未混入首轮的 27 个符合结果。
- 可以保存岗位、分析公开 JD、引用已有经历、创建“准备申请”记录、生成绑定简历版本的冻结草稿。
- 准备申请后候选状态变为 `CONVERTED`，从收藏夹转入申请看板；这是现有状态设计，数据没有丢失。
- 材料草稿保留未确认的私密字段作为阻塞项，没有自动批准或提交。原有 1 条申请保留，副本增加 1 条准备中的申请。

## 优先处理的缺陷

### P1 真实研发岗位被挡在待核实

复现：保存上述目标并搜索，在“待核实”中查看以下岗位；勾选“只看符合本次条件”后这些机会会消失。

- [蔚来 校招 Agent 开发工程师 NOMI](https://nio.jobs.feishu.cn/campus/position/7673027287931570478/detail)：官网明确为北京、正式、2027 届，本科及以上；职责明确包含 Agent 工程架构、AI Native 应用开发和 Tool Calling / API / RPC / MCP 集成。系统理由却是“关键词或岗位标题不足以确认目标研发职责”。已打开官网复核。
- [小米 Agent Harness 开发工程师](https://xiaomi.jobs.f.mioffice.cn/campus/position/7678147882801678602/detail)：正文为北京、2027 届，明确设计建设面向模型与 Agent 的 Harness 能力；系统保存了这句作为证据，却仍提示“关键词尚未绑定到目标方向的实际研发职责”。

离线重放两份 JD 均能复现。`src/services/job_role_review.py` 的 `local_duty_evidence` / `specific_direction_needs_evidence` 对表述形式过于敏感；首轮 NOMI 的语义复核还遇到了 `role_review_budget`。建议补齐动作与实现对象的识别，优先复核高相关歧义岗位，并提供单岗位“重新核对方向”入口。验收应覆盖这两份真实原文，同时保留纯基础设施、产品、运营反例。

### P1 运营策略岗位被当作 Agent 研发岗位

复现：[字节 Agent 数据策略 AI 数据与安全](https://jobs.bytedance.com/campus/position/7683449009184786741/detail) 被标为符合。官网标注“正式 运营”，要求“接受技术与运营兼具的工作状态”，核心是数据与评测体系、迭代协同和数据策略，不足以确认 Agent 系统开发职责。

系统使用第一条“数据与评测体系构建……Agent 业务场景数据需求”直接判定 `local_duties`，并跳过了模型复核。标题规则也没有识别“数据策略”这种职能。已打开官网复核，并离线复现。建议保留官网职能分类，区分“为 Agent 提供数据”与“开发 Agent 系统”，不要只依靠相邻关键词放行。

### P2 本地匹配错误处理任选语言

在字节 Data 岗位分析中，“熟悉 C++ / Golang / Python / Java 等其中一种语言”正确解析为任选关系，但已保存的 Python 经历仍只得到“部分匹配”。这降低了证据覆盖数，并产生不必要的补资料提示。

用合成证据“熟悉 Python。”离线重放，仍能复现。`src/services/ordinary_requirement_evaluator.py` 的 `requirement_sources` 没有去掉“等其中一种语言”这个共享关系尾缀，分支变成“熟悉 python 等其中一种语言”，导致后续文字蕴含失败。建议修复常见任选句式并保留能力程度，验证“任一语言满足”与“多个独立条件必须同时满足”两类场景。

### P2 载入失败后的恢复不完整

浏览器重载出现多处 `Failed to fetch`；材料弹窗刷新可恢复。岗位页点击“重试”后岗位列表恢复，但求职目标仍显示“新建求职目标”，个人资料仍显示不可用；进入资料页可以读出数据，返回岗位页才恢复目标。

首次连接失败的原因尚未确定，不能直接归咎于产品或 CORS。后端同一时间段的独立检查均为 200。确定存在的产品恢复缺口是：`frontend/app/search-goal-controls.tsx` 只在挂载时读取目标，而 `page.tsx` 的岗位刷新不重载目标与资料摘要。建议给各失败区域独立重试入口，或提供统一重新连接；同时保留已读取的内容。

附带性能观察：现有约 200 个候选的副本，候选 / 线索 / 搜索历史三个接口一次合计约 3.67 MB；搜索历史约 2.39 MB、读取 2.28 秒。搜索期间每 3 秒刷新整批历史，不适合长期积累。应增加分页与精简运行摘要，不能把此次网络失败直接归因为响应体大小。

### P2 时间显示比北京时间早 8 小时

搜索实际开始于北京时间 16:38，接口 `started_at` 却返回无时区的 `2026-10-16T08:38:42.872656`；前端 `new Date(value)` 按本地时间读取，显示 08:38。岗位核验、申请时间线及材料修订均出现同类显示。

在 `Asia/Shanghai` 下分别解析同一字符串与补上 `Z` 的字符串，可稳定复现 8 小时差异。建议统一输出带时区的 UTC 时间，再按浏览器时区展示；验收覆盖数据库读取后的时间与新建响应。

## 自用时的额外注意

- “符合已知条件”目前核对搜索目标，不检查本人的全部资格。例如首轮蔚来“车端 AI Agent 与应用生态系统架构工程师”明确要求博士，仍会出现在符合结果中。现有页面对此有文字说明，但最好在列表直接展示学历门槛。
- 同名相近岗位仍占多个位置。字节财经业务有两个不同官方 ID、职责几乎相同的岗位。不能直接删除其中一个，适合增加“相似岗位”提示与折叠。
- 申请材料能生成草稿，但仍需本人确认联系方式、就读 / 就业状态、到岗时间等字段。国内自用时，签证担保等字段应按岗位需要出现；当前弹窗还暴露 `M15`、哈希、英文枚举和字段名，操作负担偏大。
- 默认语义经历匹配、本人实际简历改写、招聘方登录和最终提交不在本次验证结论内。全程没有向招聘方投递或发消息。
