# 求职目标多查询真实复测（2026-10-12）

完成 4 种查询各 1 次空库搜索，以及上海 Agent 查询的 1 次同库更新。真实官网请求、联网搜索、方向复核模型和前端均启用，没有 mock。结果表明：后端查询的前十相关性较好；Agent 应用限定仍会丢失，复杂网页核验会造成明显长尾，默认展示来源过度集中。

## 方法与边界

- 正式链路：保存求职目标 → 发起搜索 → 岗位正文核验 → 岗位库重筛 → 实际前端展开公司列表。
- 每种查询使用独立空 SQLite；没有简历、候选人画像或经历，不触发资格分析、投递或申请。
- 保留实际配置：官网直搜开启，搜索选择策略为 `rule`，方向复核使用真实模型。搜索最多 6 轮、300 秒，目标 15 个；搜索结束后的核验队列另有 180 秒预算，单项 60 秒。方向复核批量 2、并发 2、最多 12 次、单请求 15 秒。各轮配置快照见 `runtime-settings.json`。
- 时间从保存目标请求开始，包含目标解析和 API 轮询；服务启动不计入。每 1.5 秒轮询，首条时间是后台可供展示的观测时间，未直接测浏览器首次绘制。
- 首条可用：首次在岗位库中观测到系统 `matched`，并经后续原文审计确认符合原始查询。系统误判和不确定样本不计为已确认有效。
- 前十：实际默认页面公司分组展开后的前十行，包含待核实和未核验链接；没有重新挑选“最好”的十条。
- 误排除：原文可确定的系统已排除样本中，实际有效的比例。不确定样本另列；该指标不包含系统未搜索到的岗位，不能解释为全网召回率。
- 标签由助手逐条阅读公开原文后提供，不是独立人工金标；本轮没有用匹配器结果生成参考标签。保存每条判断、理由、原文引句、URL、内容哈希并校验引句确实在原文中。
- 指定城市按“至少一个可选地点符合”解释；同时包含北京和上海/深圳/杭州的职位，可以选择目标城市。上海优先是排序偏好。Python 优先不排除其他后端语言。Java 查询按正文允许使用 Java 计，不保证岗位主栈是 Java。
- 测量前后 `src` 和 `frontend/app` 哈希一致。本轮未修复下述产品问题，不将测后修复与本次基线混用。

## 四项结果

| 查询（均排除社招） | 首条确认可用 | 总耗时 | 前十确认有效 | 误排除/可确定排除样本 | 另外不确定的排除样本 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 2027 上海 Agent / RAG / 大模型应用校招，排除北京 | 14.8 秒 | 58.6 秒 | 8/10（80%） | 0/5 | 1 |
| 2027 深圳后端校招，Python 优先，排除北京 | 11.4 秒 | 52.6 秒 | 10/10（100%） | 0/2 | 0 |
| 2027 杭州 Java 后端校招，排除北京 | 11.2 秒 | 363.0 秒 | 10/10（100%） | 0/20 | 0 |
| 上海优先，Agent 应用开发实习，不限届别 | 7.9 秒 | 62.6 秒 | 9/10（90%，另 1 条不确定） | 0/2 | 2 |

上海空库在 9.7 秒已有 3 个系统判定符合的岗位，但原文分别是预训练、可观测平台和 DevOps。前两条未明确应用研发任务，DevOps 同时探索 Agent 与工程平台结合，属于不确定边界。因此以 14.8 秒出现的明确 Agent 平台/运行时研发岗位作为首条确认可用；不能把 9.7 秒直接写成已验证可用时间。

上海同库更新：约 **0.2 秒**读取到原有符合岗位，总更新耗时 **46.2 秒**，岗位库仍为 35 条，本轮没有确认新增有效岗位。0.2 秒是岗位库复用速度，不能与空库新检索速度混称。

## 暴露的问题

### 1. 原始方向限定在保存目标时丢失

原输入含“大模型应用”，但保存后的条件是 `roles=["agent", "llm", "rag"]`，整理后的查询为“岗位方向：agent、llm、rag”。本地意图解析把“应用/应用开发”当作填充词移除。匹配器原本通过查询中的“大模型应用”识别范围限定，读取整理后的查询时已无法恢复限定；方向复核也看到了放宽后的 LLM 方向。

上海前十有两条被标为符合，但实际偏底层模型工程：

- `7678911812435544373`：LLM Infra，职责为训练/推理技术、PyTorch/TensorFlow 优化、生成式推荐架构。
- `7677864688073738501`：LLM/VLM 推理算子优化，职责为芯片适配、GPU/NPU 和算子性能优化。

应在结构化条件中保存应用、训练、推理优化等范围，而不依靠重建查询文本恢复。还需保存岗位职能，避免“Agent”字样直接等同于应用研发。

上海实习前十的“战略（Agent方向）实习生”同时搭建 Skills/工作流并承担战略研究，软件研发职责不足以明确确认。保守记为不确定，不能按系统绿色标签算进正确数。

### 2. 补搜后的浏览器核验造成长尾

杭州仅获得 10 个系统符合岗位，未达 15 个目标，因此执行全部 6 轮搜索。最终发现 108 条线索：80 条具体岗位（40 条已读正文、40 条待核验）及 28 个招聘入口。岗位库为 10 符合、10 待核实、20 排除；40 条未核验链接另存，不能混为正式岗位数。

本轮共 37 次 HTTP 核验报告需要浏览器；浏览器阶段有 11 次岗位页未核验、13 次截图提取未核验、1 次详情未确认和 2 次取消。最长核验排队约 **225 秒**。最终状态为 `PARTIAL`，原因是“正文核验预算已用尽，剩余链接已保留待核验”。

当前搜索预算与搜索后队列收尾预算分开，300 秒不是严格端到端时限。应优先为反复失败的来源限制展开和核验次数，及时保留待核验状态，并统一展示用户能理解的总耗时上限；针对真实失败网站补充可读取详情的核验方式。

方向复核也存在超时：4 个空库查询分别为 10/7/6/12 次请求，其中超时请求为 1/1/2/1 次；深圳另有 1 次响应格式错误。这里按请求事件计数，未把同一次错误的多个追踪事件重复统计。

### 3. 默认前十全部来自字节

四种查询前十都是字节跳动，不能据此宣称多企业覆盖已经足够。正式岗位库还包括 MiniMax、小米、蔚来及京东，但其他公司的相关性、核验能力和当前公司分组顺序，都影响实际用户看到的来源。

应先确保每个新增来源确实能读取有效岗位，再评估是否让默认结果展示更多公司。扩展来源不能只增加网址或招聘入口。

### 4. 不确定的已排除岗位还需验证三态边界

上海校招有 1 条标题明确 LLM 营收应用，但职责主要描述传统推荐算法，暂无法确定是否误排除。上海 Agent 实习有 2 条明确 AI/LLM 智能诊断任务、仅在加分项提到 Agent，无法确认是否属于所请求的 Agent 应用开发。

这三条均保留不确定标签，未将其计为“排除正确”。需要用职责范围验证应进入待核实还是明确排除，避免信息不足被直接处理成不匹配。

## 下一步顺序

1. 保留原始岗位方向与职能限定，让保存目标、检索、本地筛选和模型复核使用同一范围。
2. 对照杭州本轮真实失败来源，限制无效展开/浏览器重试，改善队列收尾与总耗时边界。
3. 用同样四种查询复测，再逐个扩充官网来源。每组目前只有一次空库样本，修复后需多次重复才能评价稳定性。

本轮采用规则查询选择器，不能据此评估模型选择器相对规则的收益；也未验证 JD 单次/两次解析指标或候选人资格。
